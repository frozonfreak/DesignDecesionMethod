# Acceptance criteria and validation

Pick a few criteria matched to the design. Do not use a fixed score or a universal time or click limit.

## Record format

Task and audience and device / expected outcome / metric or check / target / method / result (or "not tested").

Label each target as evidence-based (from the brief, a standard, or data) or proposed. Never fabricate a measurement.

## Examples (adapt, do not copy)

- **Portfolio.** A representative visitor can identify the service, find a relevant project, and find a way to make contact. Check with a task study. For a mockup alone, record only whether those routes and content are present.
- **Repeated operational task.** Compare completion time and correction frequency against the existing workflow under comparable conditions. Any state that must stay meaningful when the view changes (for example a selected row under a filter) stays visible where the user acts, not only in a status message.
- **Form.** Valid entries survive a validation error, and the route to correct the error is clear. Test this manually. Measure completion separately if research is available.

## Communication and landing-page checks

Select only checks relevant to the page's purpose and the change. Define the audience, task, device, expected outcome and proposed or evidence-based target using the record format above.

| Outcome | Possible check | Interpretation limits |
|---|---|---|
| Initial comprehension | Ask representative visitors to explain audience, offer and relevant next step after a brief exposure; a five-second test is one optional method | Exposure duration is a study choice, not a universal acceptance limit; follow with deeper questions where needed |
| Findability | Ask visitors to locate a relevant capability, work sample, term or audience route; observe first-click choice where useful | A visible link alone does not establish successful discovery |
| Credible evidence | Review claim-to-source links and ask visitors to distinguish supported capabilities, proposals and unknowns | Factual review and visitor trust are different observations; neither permits fabricated proof |
| Informed action or comparison | Check whether visitors understand material cost, prerequisites, limitations and what happens next before choosing | More clicks or signups do not by themselves establish an informed choice |
| Activation path, where applicable | Walk the real route from the page into signup, onboarding or first useful task, including handoff and recovery | A mockup can show a proposed route; actual activation, conversion and retention require analytics or appropriate research |

For a heuristic review, report content presence and likely obstacles. Report comprehension and task results only when participants were actually observed. State analytics scope, period and limitations when using measured outcomes; do not infer them from visual polish.

## Evidence levels

| Level | Can support | Cannot support |
|---|---|---|
| Proposed | A target to aim for | Any claim about the result |
| Heuristic review | Likely problems, effort comparisons | Task-completion rates |
| Automated check | Specific rule failures | Overall accessibility or usability |
| Manual test | Behaviour of a flow, keyboard and focus | Population-level outcomes |
| User research | Real task outcomes for the sampled users | Claims beyond the sample |

Say which level each statement rests on. Do not claim research, certification, or compliance without evidence for that claim.

## Balance

Balance speed against comprehension, error prevention, and satisfaction. Do not optimise clicks or conversion at the cost of informed choices. Re-evaluate when material changes or observed problems justify it.

## Reviews

Label every finding keep, change, or defer. Present speculative additions as optional exploration. Do not silently migrate existing design decisions when upstream guidance changes.
